1

Split the drawing, then make its views.

You own the source-to-training-data contract. The most important boundary is the original drawing’s identity.

Data format selected

Raw NDJSON is the master.

A drawing contains a variable number of strokes. Each stroke has matching arrays of x coordinates, y coordinates and point times.

drawing = [ [x[], y[], t[]], … ]

Simplified vectors remove point timing. The 28×28 bitmap files contain finished pictures, so they cannot recreate the actual drawing timeline.

Data quality rules

  • Reject broken arrays, invalid coordinates and decreasing times.
  • Keep simple drawings and valid “unrecognized” examples.
  • Preserve pauses, stroke boundaries and difficult early views.
  • Deduplicate before splitting; record every rejection.

No artist ID is available in the documented source fields. This split is drawing-disjoint; it is not proven drawer-disjoint.

No view can cross this boundary.

A finished cat in training and an unfinished view of that same cat in testing would leak the answer’s drawing style and geometry. All related views and transformations stay together.

Evidence: official dataset formats · public raw file inventory. Counts above are preparation targets, not completed downloads.

The preview uses current-prefix bounds. Offline time fractions can use the recording’s final duration to define a cut; the live model receives neither final duration nor completion percentage. A live screenshot must first apply fill, erase, undo and clear.

Training views change each epoch.

20% complete drawings and 80% random 10–90% time prefixes. One sampled view per original per epoch prevents long drawings from dominating.

Validation and test use the fixed 10%, 20%, …, 100% grid. Crop each prefix from only its visible geometry; never use the finished drawing’s bounding box.

Color is allowed in preprocessing.

“Ignore color meaning” means the answer should depend on shape. It still permits RGB-based background separation and boundary detection.

Compare background-aware ink with per-channel boundary outlines on validation. Freeze the selected method for both training and serving. Identical foreground/background colors erase visible evidence; passing is valid.

3

Adapt a small transformer; test the adaptation.

Recommended starting checkpoint

ViT-Tiny · 224 × 224

ImageNet-pretrained visual features, followed by your new 345-category classification head.

timm/vit_tiny_patch16_224.augreg_in21k_ft_in1k

~5.7M pretrained parametersLocal GPUFine-tune on Quick, Draw!

The recommendation is for task fit and feasibility. It has not been established as the most accurate sketch model.

The model sees one image.

[B, 3, 224, 224] → transformer → [B, 345]

Preserve aspect ratio. Fit visible shape to 192 pixels, center it on white, repeat grayscale into RGB and use the checkpoint’s actual normalization.

Mean = 0.5 · Std = 0.5 per channel.

No secret word, future strokes, final duration, human answers or opposing canvas enter the live model.

4

Validate the model at every drawing stage.

The validation owner checks whether the model recognizes independent drawings earlier, selects the checkpoint and passing policy, then freezes the candidate for final testing.

1 · Audit the evaluation inputs

Check that validation IDs and trajectory hashes never overlap training or final test. All ten views of a drawing stay in its original split.

Verify category IDs, fixed timestamp cutoffs, current-prefix bounds and renderer hashes. A broken manifest fails validation; it is not silently skipped.

2 · Run the same views through A and B

Use model.eval() and torch.inference_mode(). Keep the view order, preprocessor, class registry and settings fixed.

Validation makes no weight updates. Store drawing ID, true class, stage, input hash, checkpoint ID, top-k output and blank/pass status for each view. True labels stay in the offline evaluator.

3 · Inspect learning and choose an epoch

After each epoch, use the fixed 50-per-class validation subset. Track training loss, validation loss and early-stage accuracy.

Falling training loss with declining validation quality is an overfitting signal. Keep the best early-recognition checkpoint; use the agreed patience of two checks. Run the full validation set before freezing.

4 · Calibrate and choose when to pass

Fit confidence calibration on validation outputs, then sweep candidate pass thresholds and plot accuracy against coverage.

Report correct guesses over all opportunities as well as accuracy among emitted guesses. Passing on nearly everything cannot establish a useful Guesser. Lock the chosen calibration and policy before final testing.

5 · Compare candidates honestly

Compare A and B on identical validation views and equal training budgets. The provisional goal is +5 percentage points early accuracy, with at most 2 points lost on complete views.

Report the actual difference and uncertainty even if the goal is missed. Bootstrap whole drawings, keeping all their stages together. Evaluate public-hint-assisted behavior separately from sketch-only recognition.

6 · Freeze, then test once

Record the chosen weights, label hash, preprocessor, calibration and passing policy. Then the validation owner runs the separate 172,500 final-test drawings.

No test-based threshold or model changes under an “untouched test” claim. A revised candidate needs an explicitly revised evaluation protocol. GPU latency and game integration follow in the next section.

What the validation owner must hand back
  • Stage report: A/B top-1 curves at all ten stages, early means and complete top-3.
  • Error report: per-class results, confusion pairs and reproducible example IDs.
  • Policy report: pass threshold, calibration settings, coverage and conditional/overall correctness.
  • Reproducibility record: manifest, input, model and preprocessing hashes plus evaluation settings.
  • Final test report: frozen A/B results and whole-drawing uncertainty estimates.

These are required future reports. No measured accuracy values are shown here because training and evaluation have not run.

5

Recognize often. Count scheduled attempts.

A recognition update is an observation. A counted guess is a version-checked game action owned by NestJS.

Frequent updates

About once per second.

Skip unchanged images. Coalesce obsolete pending updates. Keep weights loaded. Scheduled attempts receive priority.

Hidden update results do not become extra counted guesses. Cached output is reusable only for the exact permitted input/version/configuration.

Counted opportunity policy

One word, or a pass.

A 60-second demo example has opportunities at 10, 20, 30, 40, 50, 58 seconds. Blank or uncertain input may pass; no replacement opportunity.

Timing remains configurable. A pass is not an outage. An actually late response cannot score after the round/challenge deadline.

8

What the evidence must show.

Recognition over drawing progress

  • Top-1 at every 10% stage, plus full-image top-3.
  • Early-stage mean, per-class support and confusion.
  • Whole-drawing uncertainty estimates.
  • Pass rate and accuracy together with coverage.
  • Sketch-only and hint-assisted results separately.

Provisional adaptation goal: +5 points early top-1, with no more than 2 points full-image loss versus A. It is a project goal, not an assured outcome.

One laptop, up to three teams

  • p50/p95 capture-to-result, including queue time.
  • One, two and three active streams.
  • Scheduled jobs under frequent-update traffic.
  • Correct cancellation, deadlines and input versions.
  • Background/fill and training/serving image parity.

Provisional target: p95 ≤ 1 second with three teams. No latency result is available yet.

Dataset size does not establish game transfer.

There is no new player drawing set in this plan. The group will report held-out Quick, Draw! results and synthetic robustness checks. Accuracy on real filled, edited game drawings and human-beatable difficulty remain unverified.
